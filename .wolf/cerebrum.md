## Key Learnings
- TWO LEDGERS, always ask which one a number is. `lu.actual`/`lu.gkActual`/`lu.app` are whole-game PROJECTIONS — buildPeriods stamps every planned period frac:1 and tally() adds +1 for the rest of the game the moment a sheet is built. Only `playedThrough()` (and `ivPlayed()`) give banked time. Display surfaces need banked; build-time fairness ordering needs the projection. Before touching any playtime number, decide which. See [[bug-156]].
- Discounting the live period is NOT a blanket subtraction once you filter by position. Unfiltered it works because a mid-period swap leaves the two entries summing to 1; filtered to GK (or D/F) that invariant is gone and a blanket discount double-charges. Trim only `activeEntry()` — the entry actually running. Both `playedThrough(...,pos)` and `positionTotals(...,live,rem)` rely on this.
- User's stated goal for Game Day: a majority of the screen must serve split-second decisions, with some season/multi-game context alongside. Season stats belong there — they just have to be numbers you can act on without mentally subtracting the plan.
- Game Day tests should simulate a full realistic game (4 periods, a sub each period, a keeper swap, breaks, half-time) and assert invariants at every beat, not just at full time. See `test/credit.test.mjs` and `test/played.test.mjs` for the pattern: mirror the app.js wrappers (`remFrac`, `curPi`) in the test file and drive a `g` object.
- Negative control is cheap and worth it: `sed` the test file's wrappers back to the pre-fix versions into `test/negcontrol.mjs` (not `*.test.mjs`, so `npm test` ignores it), run, confirm it fails, delete. Proves the test guards the behaviour rather than the implementation.
- Web push: the period alarm is server-fired because a locked phone runs no app JS. Client registers a deadline with POST /api/team/:id/alarm on every clock start and cancels on every stop — syncAlarm() sits beside syncWake() in startTicker/stopTicker, which are the two funnels every running-state change passes through.
- The push is deliberately PAYLOAD-LESS: VAPID auth only, empty body, so there is no aes128gcm/ECDH encryption code at all. The notification text lives in sw.js. The full PushSubscription is still stored in push_subs.sub, so encryption can be added later without re-subscribing anyone.
- GameClock is a SQLite-backed Durable Object (new_sqlite_classes) — the only kind the Workers Free plan allows. One instance per team via idFromName(teamId), so a second device just moves the same alarm.
- Anything in app.js that reads TEAM/KEY/state must be called from boot(), not run at parse time: the file is one IIFE and TEAM is assigned inside boot() at the bottom. See [[bug-032]].
- Testing push: pushManager.subscribe() is unreliable in headless Chrome (FCM). Stub it and assert our own downstream calls; drive sw.js with CDP ServiceWorker.deliverPushMessage instead. See [[bug-033]].
- Sensors: a PWA on iOS gets DeviceMotion/DeviceOrientation (permission-gated), geolocation, getUserMedia and Screen Wake Lock (Safari 16.4+) — and nothing else. No proximity, no ambient light, no vibration, and no web API on any browser can dim or blank a screen. Proximity-blanking is native-only (UIDevice.proximityMonitoringEnabled), so it is a Capacitor feature, not a PWA one.
- Pocket lock (#lockScreen) is armed explicitly by the coach, never automatically on Start — a coach taps subs and goals constantly during a period, so a self-arming lock fights them. Unlock is an 800ms press-and-hold (a short tap must not unlock, that is the whole point).

The per-element restatements on `.lockscreen` and `.toaststack` were removed as dead weight. Do not re-add font-family to individual containers; fix `body` if a font problem appears.

- **`playedSoFar()` is ELAPSED clock time, not the plan** (changed 2026-08-04). `lu.app` fracs are *allocations* — "the share of this period you will play" — and `buildPeriods` stamps every entry `frac:1` at build time, so summing them read a full period for everyone at kickoff, before a ball moved. `LineupCore.playedThrough(lu,pi,id,live,rem)` discounts the period on the clock by the share still unplayed. Key facts: only the player **currently in `lu.periods[live]`** is discounted (a sub already trimmed the outgoing player's entry to exactly what they played — do NOT use `activeEntry()` for this, it means "has frac left" and still matches a subbed-off player); periods after `live` contribute zero; the two definitions **converge exactly at every period boundary** (`rem=0`), which is where the guide's "3 of 4" rule is judged.
- `remFrac()` in app.js: 1 before kickoff, **0 during a break** — `g.secs` is the break's own countdown and `curPi()` still points at the period that just ended, so feeding the break clock into the elapsed math would corrupt every total.

- Switching to elapsed does **not** change the sub recommendations. Every on-field player gets the same `− rem`, so their relative order is fixed; bench players get no discount, and the two ranked lists are paired by index, never compared against each other. Measured, not assumed.
- The `.pp` half pip means "a sub split one of their periods" — computed from the PLAN via `wasSplit()`, never from the displayed value. Under elapsed timing every chip is fractional mid-period, so testing the display would pip nearly all of them.

The URL's `token` is a bearer credential: never commit one to the repo or bake it into client JS.

- **The team passphrase is OPT-IN and the session cookie is signed with `teams.pass_hash` itself.** No `SESSION_SECRET` env var exists and none should be added — the hash is already a per-team server-side secret, and using it as the HMAC key means changing the passphrase logs every device out for free (that is the revocation story; there is deliberately no sign-out endpoint, because the whole team is still in localStorage on that device anyway). `gate()` runs before every `/api/team/:id*` route except `/auth`; a team with `pass_hash IS NULL` behaves exactly as it did pre-lock, so no existing share link breaks.
- **PBKDF2 is 10,000 iterations because Workers Free allows 10 ms CPU per request.** Measured with node's WebCrypto (same BoringSSL shape): ~0.5 ms per 1000 iterations — 100k would be ~49 ms and blow the budget on every login. The count is stored in the hash string (`pbkdf2$iters$salt$hash`), so raising it later verifies old hashes at their own count. Check `validSession` (HMAC, microseconds) BEFORE `verifyPass` (KDF) so a logged-in device changing its passphrase pays for one derivation, not two.
- Login rate limiting is the native `ratelimits` binding (`LOGIN_LIMIT`, 10/min), keyed on the **team id, not the IP** — a distributed guesser rotates IPs, and the cost of the stricter key (a team under attack cannot log in for 60s) is nothing on a local-first app. It is checked before any D1 read or KDF, so a 429 costs nothing. The worker treats a missing binding as "no limit" so local dev still works.
- **Security headers come from `public/_headers`, native to Workers static assets** (wrangler logs "✨ Parsed 1 valid header rule" on boot). `/api/*` responses are minted in `json()` and set their own `nosniff`. The CSP allows no external origins and no inline scripts; `'unsafe-inline'` is on `style-src` only, for the `style=""` attributes in index.html — verified 0 violations driving the real UI in headless Chrome.
- `ask()` takes `pass:true` for passphrase fields: `type=password` plus `autocapitalize="none" autocorrect="off"` — a phone silently autocapitalising a passphrase is a lockout. Setting one asks **twice** and compares client-side, because there is no reset path. The server trims both ends for the same reason.

They just fail and retry, which is the app's normal offline behaviour. `afterLockChange()` re-reads them once after a lock/unlock, which is the in-flight-401 window. See [[bug-126]].

## Do-Not-Repeat

- [2026-08-05] **An author `display` rule on a `<dialog>` beats the UA's `dialog:not([open]){display:none}`.** `dialog.sheet.cardsheet{display:flex}` left the closed player card rendering in normal flow at the foot of `<body>`. Scope layout display to `[open]` (`dialog.sheet.cardsheet[open]{display:flex}`) and keep only box metrics on the base rule. Same family as the `hidden` attribute losing to `.clock-band{display:flex}` — a UA or attribute default never wins against an author rule. See [[bug-138]].


- [2026-08-05] **`TaskStop`/Ctrl-C on `wrangler dev` does NOT kill `workerd.exe` on Windows.** The orphan keeps the port bound and keeps serving the OLD bundle against the OLD `.wrangler/state` D1, so every later "Ready on http://127.0.0.1:8788" is a lie and the responses come from a zombie. This cost three wrong theories (`--persist-to` ignored, `d1 execute` vs `dev` keying differently, `database_id` mismatch) — the flag was working the whole time. Before trusting ANY local verification: `Get-Process workerd | Stop-Process -Force`, then confirm with `Get-NetTCPConnection -LocalPort <p> -State Listen` + `Get-CimInstance Win32_Process` that the listener's `CreationDate` is after you started the server. Orphans from previous days were still running. See [[bug-125]].
- [2026-08-05] To exercise a schema change locally without touching the user's dev D1, copy wrangler.jsonc to a temp config in the project root with a different `database_id` and run both `d1 execute -c` and `dev -c` against it — that mints a brand-new sqlite under `.wrangler/state/v3/d1/<newhash>.sqlite`, leaving existing files untouched. Delete the temp config and the new file afterwards. (Keep the config in the project root: `main` and `assets.directory` are relative paths.)
- [2026-08-04] **`position:sticky` only sticks within its own parent's box.** `.clock-band` was made sticky in place, inside the left `.gd-grid` column, and unstuck the moment that short column scrolled past — it looked like sticky "not working". It had to be moved out of the grid to be a direct child of `section#p-game`. Before adding sticky, check what the parent element's height actually is, not what the page's is. See [[bug-074]].
- [2026-08-04] **An `opacity` keyframe is only safe on an element with nothing behind it.** `@keyframes clockflash{50%{opacity:.35}}` was fine on the in-flow clock band and made it see-through the instant the band became sticky and started overlapping page content. Flash `background-color` instead for anything pinned. See [[bug-075]].

- [2026-08-04] **Never write `.wolf/*.json` with PowerShell.** `ConvertTo-Json | Out-File -Encoding utf8` on Windows PowerShell 5.1 emits a UTF-8 **BOM**; the OpenWolf hook parses these files with `JSON.parse`, which throws on a BOM, and the hook then reinitialises the file and renumbers from bug-001. This destroyed buglog.json entries bug-005..045 (working-tree only, never committed, unrecoverable). Use the Write/Edit tools for these files — they write UTF-8 with no BOM. Same hazard for any file another tool parses: `Set-Content`/`Add-Content -Encoding utf8` and `>`/`>>` all risk a BOM here. Verify with `[System.IO.File]::ReadAllBytes(p)[0..2]` — `239,187,191` means a BOM.
- [2026-08-04] The `hidden` attribute loses to any author `display` rule — `.clock-band{display:flex}` made a JS-hidden element render. app.css now carries a global `[hidden]{display:none!important}` guard; keep it, and don't rely on `hidden` alone for elements with their own display rule.
- [2026-08-04] `opacity:0` does not remove layout. `.fabmenu` (the FAB nav's closed dropdown) was a normal in-flow flex child with `opacity:0;pointer-events:none` — invisible but still ~280px tall, and only the *inner* element had `pointer-events:none`, not the outer `.fabnav`. Clicks landing in that invisible region hit the nav (default `pointer-events:auto`) and never reached page content underneath — e.g. "Build lineup" went dead at some viewport heights, no console error, no thrown exception. Symptom looked exactly like an app logic bug (silently-false return) and cost a long debugging detour through sync/race-condition theories before the actual cause (a layout/hit-testing issue) surfaced. Fix: any hidden-via-opacity dropdown/menu must be taken out of flow (`position:absolute`) so its closed state contributes zero size to the container. When a button "does nothing" with no error, check for an invisible overlapping element before suspecting the click handler's logic.

## User Preferences (cont.)

- Controls must *look* like controls: a bare text label (the old roster "IN") reads as a status, not a button. Prefer making the whole row tappable with a pill-styled state chip.
- Destructive/irreversible game-day controls (Reset, Period +) get a confirm gate; put each control *on* the thing it changes, not merely near it — Reset is now an edge tag on the clock row itself (mirroring Edit), Period + sits by the period badge.
- A control that is only correct in one situation should withdraw itself rather than rely on the confirm sheet to warn. Reset is a false-start tool; it hides once the period's clock has been used as a credit boundary instead of asking the coach to reason about ledger consequences mid-game.
- When a control appears/disappears in a fixed slot, position it absolutely so the toggle costs zero layout — the surrounding controls must not move under a thumb.
- Critical notifications must persist and stack until dismissed — no auto-fading a substitution message a coach hasn't read.
- Copy in a fixed slot must not change height between states — reserve the space so nothing reflows under a thumb mid-tap.
- On phones the primary panels (clock, On the field) go edge to edge; keep the section background colours so the boundaries stay legible.

## Decision Log
- 2026-08-04: Web push over a Capacitor/native watch app. Push needs no Mac, no $99 developer account and no App Store, works on Android too, and solves the actual problem (feel the whistle without touching the phone). Cost is a Durable Object for exact-second scheduling — Cloudflare cron is 1-minute granularity, far too coarse for a whistle.
- 2026-08-04: **Reset stays, scoped to false starts, rather than being deleted.** "Set the clock" (tap the clock) already covers every Reset case and is logged + undoable, so deleting Reset was on the table. Kept because the false-start case (ref not ready, clock bled off before kickoff) is 2 taps vs ~5 and happens in a hurry. Everything past that moment routes to Set the clock. Rejected outright: having Reset roll the period's credit back — `lu.app` entries are additive fractions across overlapping subs, and "undo the clock running" is not the same operation as "undo the sub", so there is no unambiguous inverse. Credited playing time is never rewritten by a clock control.
- 2026-08-04: Chose a PWA pocket lock + wake lock over a Capacitor wrapper for the stray-tap/alarm problem. Capacitor was planned (see the iOS haptics thread) but gated on a Mac, $99/yr and a rebuild loop; the lock overlay needs none of that and solves the actual complaint. Capacitor stays on the table only for backgrounded local notifications and UIImpactFeedbackGenerator — the two things a PWA genuinely cannot do.
